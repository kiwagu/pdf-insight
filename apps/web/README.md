# web

The PDF Insight single-page app: Vite, React 19, Tailwind CSS v4 and shadcn/ui on Base UI. It
reads the PDF in the browser, sends the extracted text (and images of pages without a text
layer) to the analysis API, validates the answer against the shared contract and keeps the last
analyses in this browser.

## Role in the architecture

The app is the browser-side adapter layer around `@pdf-insight/domain`. The domain's
`analyzeDocument` use case drives an analysis through three ports, and this package implements
each of them:

- `TextExtractor`: `createPdfJsExtractor()` reads every page with pdf.js, rebuilds the reading
  order of the text items and renders pages without a usable text layer to JPEG (at most
  `MAX_SCANNED_PAGES`). Any failure to open or read the file surfaces as `extraction_failed`.
- `DocumentAnalyzer`: `createHttpAnalyzer(baseUrl)` posts the extracted document to the API,
  parses the response envelope with the contract schema and maps transport failures to
  `network`, unparseable or off-contract bodies to `invalid_response` and API error envelopes
  to their own code. Requests time out after 90 seconds.
- `AnalysisHistory`: `createLocalStorageHistory(storage)` keeps the newest ten results under
  `pdf-insight.history.v1`, validates what it reads back and falls back to memory when storage
  is unavailable or full.

`createContainer()` wires the three adapters together. Before an upload reaches the use case,
`validatePdfFile` rejects files over 10 MB and anything that does not start with the PDF magic
bytes, and `exceedsPayloadCap` flags documents whose request would exceed the API body limit.
The UI state is a small reducer (`idle`, `extracting`, `analyzing`, `done`, `error`), and every
error code maps to an `error.<code>` message of `@pdf-insight/i18n` (Polish by default, English
on request, the choice kept in `localStorage`).

## Layout

- `src/app/`: the app shell, the state reducer and the dependency container.
- `src/api/`: the HTTP client for the analysis API.
- `src/lib/`: browser helpers: file checks, JSON download, the i18n provider and hooks, the
  pdf.js extractor and its text and payload helpers (`lib/pdf/`), the history store
  (`lib/history/`) and the `cn` class helper (`lib/utils.ts`).
- `src/components/ui/`: shadcn/ui primitives on Base UI (`@base-ui/react`), generated by the
  shadcn CLI from `components.json` (style `base-vega`) and committed as source.
- `src/styles/global.css`: Tailwind, the theme variables and the dark scheme, which follows the
  operating system through `prefers-color-scheme`.

## Configuration

`VITE_API_URL` is the full URL of the analyze endpoint and is read at build time. The app is
served under the `/pdf-insight/` base path.

## Browser support and scanned pages

The extractor loads pdf.js from its legacy build (`pdfjs-dist/legacy/build`), which includes
polyfills for the newest built-ins the default build relies on, so PDFs also open in browsers
that are a few releases behind. Scanned pages are often JBIG2 or JPEG 2000 images, which pdf.js
decodes with WebAssembly modules. Before `dev` and `build`, `scripts/copy-pdfjs-wasm.ts` copies
those modules and the ICC profiles from `pdfjs-dist` into `public/pdfjs/` (generated, not
committed). Vite serves them as `<base>pdfjs/wasm/` and `<base>pdfjs/iccs/`, and the extractor
passes these paths to pdf.js as `wasmUrl` and `iccUrl`.

## Scripts

- `VITE_API_URL=http://127.0.0.1:55351/functions/v1/analyze bun run dev`: local development
  against a locally served function.
- `bun run build`: type-check and build into `dist/`; a deployable build needs `VITE_API_URL`.
- `bun run test`: Vitest in a jsdom environment over `src/**/*.spec.ts(x)`.
- `bun run lint`, `bun run typecheck`: ESLint and `tsc` with the shared workspace configs.
